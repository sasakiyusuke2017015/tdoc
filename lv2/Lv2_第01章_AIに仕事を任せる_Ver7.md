## この章で学ぶこと（学習目標）

この章を終えると、以下ができるようになります。

- AIに「仕事を任せる」とはどういうことかを、自分の言葉で説明できる
- 自分の業務を複数の工程に分解し、AIに任せる部分と自分が行う部分を区別できる
- 依頼前・実行中・完了後のそれぞれで、何を確認すべきかを具体的に説明できる
- 一つの業務を、依頼から確認・修正・完了・効果の記録までの一連の流れ（Workflow）として捉えられる
- 実際にAIを使ってタスク分解表と依頼文を作成し、AIの出力を確認・修正できる

Lv.2は「自分の実務の中で生成AI活用を成立させ、業務上の成果につなげられる人」を目指すレベルです。第1章は、その土台となる考え方と流れの全体像を扱います。

## 1.1　「AIに仕事を任せる」とはどういうことか

生成AIを使うとき、多くの人は最初「質問して答えをもらう道具」として使い始めます。しかし、Lv.2で求められるのは一歩先の使い方です。それが、本教材で扱う **AI Delegation（AIへの仕事の委任）** という考え方です。

「AI Delegation」という言葉自体は、使う人や文脈によって指す範囲が一定ではありません。そこで本教材では、次の意味で使います。

> **本教材におけるAI Delegationとは、最終的な責任と判断は人が保持したまま、AIに任せる範囲・渡す情報・確認方法・完了条件を人があらかじめ決めたうえで、本来自分が行うはずだった作業の一部をAIに任せることです。**

人に仕事を任せるときのことを思い出してみましょう。私たちは後輩や部下に仕事を任せるとき、無意識に次のようなことをしています。

| 人に任せるときにしていること | AIに任せるときも同じことが必要 |
| --- | --- |
| 何を、どこまでやってほしいかを伝える | 目的・範囲を明確に指示する |
| 必要な資料や背景情報を渡す | 判断に必要な情報を与える（第3章で詳述） |
| 一度に全部ではなく、区切って依頼する | 作業を分解して依頼する |
| 途中経過やアウトプットを確認する | 出力を確認し、必要なら手直しを指示する |
| 最終的な責任は自分（依頼者）が持つ | 最終的な判断・責任は人間が持つ |

<!-- 画像案：人からAIへ、仕事の一部を委任するイメージ -->

つまりAI Delegationとは、AIを「何でも自動でやってくれる魔法の箱」として扱うのではなく、「指示すれば動いてくれる有能なアシスタント」として扱うということです。この前提を持てるかどうかが、Lv.2とそれ以前の使い方の一番大きな違いです。

### 委任の深さと利用形態

AIへの委任には段階があります。単発の質問に答えてもらう**チャット**から、指示・参照資料・会話を業務単位でまとめる**プロジェクト機能**、複数の工程やツール利用をある程度自律して進める**エージェント**まで、任せ方は連続しています。後になるほどAIに任せる作業範囲は広がりますが、人が決めるべき目的・権限・確認ポイント・完了条件が不要になるわけではありません。

この章ではまず、どの利用形態にも共通する「作業を分け、人が確認して完了させる」基本を扱います。プロジェクト機能は第2章・第3章、ツールや業務システムを使うエージェント的な活用は第7章・第9章以降で詳しく扱います。

### 委任の前に知っておくAIの動作

チャット型生成AIの多くは、**LLM（大規模言語モデル）** を基盤にしています。LLMは大量の文章から、文脈に続きそうな語や文字の断片（**トークン**）を一つずつ予測して出力を組み立てます。これはデータベースの内容を常に検索・照合して答える仕組みとは異なります。もっともらしい続きが作れても、事実を裏取りしてから回答しているとは限りません。

同じ依頼でも実行ごとに表現や内容が変わることがあります。これは次のトークンの選択に揺れがあるためで、**出力の非決定性**と呼びます。1回の出力や比較だけで「常に正しい」「この指示なら必ず同じ結果になる」とは判断せず、重要な成果物は確認します。

また、モデルがあらかじめ学習した知識には期限（**ナレッジカットオフ**）があります。最新の製品仕様、ライブラリの現行版、脆弱性情報などを確認するときは、モデルの記憶だけに頼らず、第7章のWeb Searchなどで公式情報を確認します。

### モデルと利用手段を選ぶ

同じAIサービスでも、速度・コスト重視のモデルと、複雑な比較・設計・原因分析に向く推論重視のモデルやThinking系のモードが用意されている場合があります。定型的な要約・翻訳・形式変換には前者、複数の条件を踏まえた分析や設計レビューには後者を検討します。ただし、推論重視のモデルを使っても事実確認や人の承認が不要になるわけではありません。

さらに、同じモデルでも、履歴・検索・ファイル添付などを備えた**チャットアプリ**と、開発者が呼び出し方や設定を制御する**API**では、利用できる機能や挙動が異なります。AIの回答を比較・説明するときは、モデル名だけでなく、どの製品・機能・設定で使ったかも確認します。

## 1.2　仕事を「任せられる単位」に分ける（Task Decompositionの基礎）

「この仕事、AIにお願いできる？」と漠然と考えても、多くの業務はそのままではAIに渡せません。理由は単純で、多くの業務は複数の作業の集合体だからです。

この一つひとつの作業単位に分けることを **Task Decomposition（タスク分解）** と呼びます。AIに仕事を任せるときは、この分解が最初の一歩になります。実際の例で見てみましょう。

### 例1：システム開発（仕様書ドラフトを作る）

「実装内容に合わせて仕様書を作る」という業務は、実際には次のような工程に分かれています。

1. 実装内容と変更差分を確認する
2. 仕様書に必要な項目を整理する
3. AIに仕様書のドラフトを作らせる
4. 実装内容とドラフトの齟齬を確認する
5. 誤りや不足を修正する
6. 完成した仕様書を提出する

### 例2：システム運用（障害の一次報告を作る）

「障害発生時に一次報告をまとめる」という業務も、同じように分解できます。

1. ログと監視情報を確認する
2. 発生時刻、事象、影響範囲を整理する
3. AIにログ要約と一次報告文のドラフトを作らせる
4. 原文と照合して事実関係を確認する
5. 未確認事項を断定していないか確認する
6. 修正後に報告文を送付する

どちらの例も、③でAIに任せ、④・⑤で人が確認・修正するという構造は共通しています。この一つひとつの工程に分けることで、次のようなメリットが生まれます。

- AIが得意な部分と苦手な部分が見えるようになる（例：ドラフト作成や要約はAIが得意、最終的な事実確認や判断は人の役割が大きい）
- どこまで一度に任せてよいかが判断できる
- 途中で確認・修正ができるようになる（任せっぱなしを防げる）

### AIに任せる作業を判断する目安

生成AIは、既存の情報を読み替えたり、型に沿って下書きを作ったりする「パターンの変換」が得意です。たとえば、要約、翻訳、言い換え、形式変換、ドラフト作成、アイデア出し、コードの雛形作成は、候補として検討しやすい作業です。タスク分解表の「AIに任せる内容」を埋めるときは、まずこうした作業が含まれていないかを探します。

一方、桁数の多い計算、厳密な文字数の遵守、最新情報の確認、正確な引用、存在しないことの確認は、生成結果だけでは保証できません。文字数を数えたり数値を集計したりする工程では、コード実行機能や表計算ソフトで確認する、人が確認する、といった別の手段を組み合わせます。「200字以内」のような厳密な条件は、出力に任せきりにせず、作成後に実測して確認します。

つまり、AIが苦手な作業を「やらせない」のではなく、**AIの出力をどの手段で確かめるかまでを工程として設計する**ことが重要です。最新情報は検索、計算は実行・集計、業務上の判断は人の確認へ振り分けましょう。

ほかにも、業務によっては次のような分解が考えられます。短い例として押さえておきましょう。

- 生成コードのロジックを追い、テストしてから提出する（システム開発）
- IaCコードの権限設定を確認し、最小権限になっているか検証する（インフラ構築）
- 顧客向け報告書を生成し、数値・事実・表現を確認してから送付する（システム運用）
- 診断結果の報告書ドラフトをAIに作らせ、人が最終判断する（セキュリティ）

タスク分解の詳しいやり方（どこまで細かく分けるか、分解の型など）は第4章「仕事を分解してAIと進める」で扱います。第1章の時点では、まず次のことが目標です。

## 1.3　任せっぱなしにしない：Human in the Loop

AI Delegationで最も誤解されやすいのが、「任せる＝依頼する範囲さえ決めておけば、あとは結果を確認せず使ってよい」という理解です。しかし、Lv.2で求められる活用は、「安全利用や出力確認を意識して活用できている」ことが前提条件になっています。

ここで重要になるのが **Human in the Loop（ヒューマン・イン・ザ・ループ、以下HITL）** という考え方です。

正しくは、次のように理解してください。

> 依頼前には、AIに任せる範囲、渡してよい情報、完了条件を決める。生成結果は、業務への影響に応じた方法で人が確認する。長時間または複数工程の作業では、実行中にもチェックポイントを置く。

<!-- 画像案：人がAIの出力を確認・検証するイメージ -->

### なぜHITLが必要か

生成AIは非常に流暢に、自信を持っているように見える出力を返しますが、その内容が常に正しいとは限りません。事実と異なる内容をもっともらしく生成すること（**ハルシネーション**と呼ばれる現象）もあり得ます。したがって、次の点が不可欠です。

- AIが出した内容を鵜呑みにせず確認する
- 業務に影響が大きい判断（顧客への提案内容、社外への発信、権限設定、金額や数値など）は必ず人間が最終確認・承認する
- 間違っていた場合に気づいて修正できる体制にしておく

また、人は機械の出力を自分の判断より過信してしまうことがあります。これを**オートメーションバイアス**と呼びます。流暢で断定的な文章ほど「もっともらしいから正しい」と受け取りやすく、確認が形式だけになりがちです。HITLは単に担当者を置くことではありません。根拠や原文と照合し、違和感があれば止める、という確認行動まで含みます。

なお、AIが「承知しました」「この条件で対応できます」と返しても、それだけでは指示を正しく満たせる保証にはなりません。確認する対象はAIの宣言ではなく、実際に出力された成果物です。

### Before・During・Afterで確認すること

| タイミング | 確認する内容 |
| --- | --- |
| ① 依頼前（Before） | ・AIに任せる範囲<br>・人が保持する判断<br>・完了条件<br>・入力するコード、ログ、設定ファイル等に、認証情報、個人情報、顧客情報などが含まれていないか |
| ② 実行中（During） | ・AIが前提や目的から外れていないか<br>・中間成果物に誤りや不足がないか<br>・AIの「できた」という宣言ではなく、成果物が条件を満たすか<br>・次工程へ進めてよいか |
| ③ 完了後（After） | ・事実と一致しているか<br>・数値が正しいか<br>・コードや設定が意図どおり動作するか<br>・テスト結果が期待どおりか<br>・権限が必要以上に広くないか<br>・顧客や社外へ送付できる表現になっているか<br>・未確認事項を事実として断定していないか |

これらの確認項目を、具体的にどう検証するか（何を、どのツールで、どんな基準で確認するか）は第6章「AIの出力を評価・検証する」で扱います。第1章では、まず「何を確認すべき対象として持っておくべきか」を押さえておきましょう。

なお、依頼前に入力情報を確認すること（**入力情報の取り扱い**）は、どの領域の業務でも共通して必要になる基本動作です。認証情報や個人情報をAIに渡してしまうこと自体がリスクになるため、Task DecompositionでAIに渡す情報を選ぶ段階から、この確認を組み込んでおく必要があります。

サービスの無料版・個人向け有料版・組織契約では、利用できるモデルや機能、利用回数の上限、入力データの取り扱いが異なります。業務情報を扱う前に、自組織が認める契約・アカウント・設定であることを確認してください。個人の無料アカウントへ業務情報を入力してよいとは限りません。

生成物を業務で使う場合も、AIが作成したことは内容の正確性や第三者の権利侵害に対する免責にはなりません。組織の規程と利用サービスの規約を確認したうえで、最終的な責任を人が負う前提で確認・承認を行います。

## 1.4　仕事の流れとして捉える：Workflowという視点

ここまでの話をつなげると、AIとの仕事の進め方は次のような一連の流れとして捉えることができます。

① 仕事全体と目的を把握する


② AIに任せられる単位へ分解する


③ AIに任せる範囲と、人が判断する範囲を決める


④ 必要な情報と完了条件を示してAIへ依頼する


⑤ AIの出力を確認する


⑥ 必要に応じて修正または再依頼する


⑦ 完了条件を満たしたことを人が判断する


⑧ 作業時間、品質、手戻りなど、AI活用による変化を記録する

<!-- 画像案：AI活用の基本サイクル（Workflow） -->

この一連の流れを **Workflow（ワークフロー）** と呼びます。ここで言う「完了条件」とは、その工程を終えてよいと判断する基準のことです（**Definition of Done** と呼ばれることもあります）。ポイントは、⑦で終わりにしないことです。「AI活用を成立させた」だけでなく、⑧のように「どのような業務成果や変化があったかを記録し、説明できる」ところまでを一つの流れに含めます。これは、Lv.2の期待状態である「自分が何を行い、どのような変化があったかを説明できる」に直接つながります。

記録する変化は、工数削減だけに限りません。例えば次のような観点があります。

- 作業時間の短縮（例：一次報告の作成が30分から10分になった）
- 抜け漏れの減少（例：確認項目の見落としが減った）
- 品質の向上（例：報告文の表現の揺れが減った）
- 初動の迅速化（例：障害対応の当たりをつけるまでの時間が早まった）
- 手戻りの削減（例：修正の往復回数が減った）
- 実装や検証など、人が行うべき作業へ時間を再配分できたこと

この視点は、本教材の後半でさらに具体的に扱います。第4章では②の分解方法を、第6章では⑤・⑥の確認方法を、それぞれ詳しく学びます。そして第11章では、自分が繰り返し行う業務に、この流れを具体的に組み込みます。第1章では、①〜⑧が一つながりの流れであり、自分はその流れ全体の設計者・責任者である、という感覚を持てれば十分です。

### 実務例：共通指示ファイルとWorkflowの具体化

AIへ毎回同じ前提（コーディング規約、レビュー観点、禁止事項など）を伝え直す代わりに、繰り返し使う前提をファイルにまとめ、AIに参照させる仕組みを使っている開発現場があります。ここでは、この仕組みを実務例として示します。

- **抽象概念**：AIへ渡す前提の再利用
- **成果物・仕組み**：リポジトリに置く共通指示ファイル。プロジェクトの規約、禁止事項、確認してほしい観点などを記述しておく
- **製品例**：`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.github/copilot-instructions.md` など（ファイル名や対応するAIサービス・機能は、利用している製品や設定によって異なります）

共通指示ファイルを置いても、確認・承認の要否は変わりません。AIが生成したコードや設定は、引き続き人が差分（`git diff`）を確認し、テストやLint、CI（継続的インテグレーション）の結果を確認し、Pull Requestとして人がレビュー・承認したうえでマージ・リリースします。共通指示ファイルは、この確認・承認の手前にある前提共有を助けるものであり、確認・承認そのものを省略してよい理由にはなりません。

例えば、①〜⑧のWorkflowを、システム開発の一場面に当てはめると次のようになります。

| Workflowの工程 | 具体例 |
| --- | --- |
| ①仕事全体と目的を把握する | Issue（課題管理システム上のチケット）に書かれた要件と受入条件を確認する |
| ②〜④ AIへ依頼する | 共通指示ファイルの前提を踏まえ、AIに実装案・コード変更を依頼する |
| ⑤出力を確認する | 生成された差分（`git diff`）を確認し、テスト・Lintを実行する |
| ⑥修正または再依頼する | テストが失敗した箇所や規約に沿わない箇所を指摘し、直させる |
| ⑦完了条件を満たしたと判断する | Issueの受入条件を満たし、CIが成功し、Pull Requestが人によりレビュー・承認されている |
| ⑧効果を記録する | 対応時間や手戻り回数などを記録する |

Issue、受入条件、CI、Pull Requestといった成果物の名称や仕組みは、利用しているツールや組織のルールによって異なります。ここでは、Workflowと完了条件を実務の成果物と結び付けるための一例として捉えてください。

## 1.5　実践演習：AIへの委任計画を作る

ここまでの内容を、実際にAIを使って体験してみましょう。この演習では、自分の担当業務を一つ選び、AIと一緒にタスク分解表を作り、その提案を自分で確認・修正するところまでを行います。

### 進め方

1. 自分の担当業務を一つ選びます。定型的な業務でも、今取り組んでいる業務でも構いません。
2. その業務の概要を、AIへの入力用に整理します。**このとき、認証情報、顧客の個人情報、社外秘の数値などは入力しないでください。** 所属組織や案件のルールを確認し、入力できない情報は削除するか、内容を再現しないダミー値へ置き換えてください。単なる言い換えでは、機密性が失われない場合があります。
3. 整理した業務概要をAIに渡し、作業工程に分解するよう依頼します。
4. AIの提案を、次の列を持つ表に整理します。

| 工程 | AIに任せる内容 | 人が行う内容 | 人が確認する項目 | 完了条件 | 効果を確認する方法 |
| --- | --- | --- | --- | --- | --- |
| （例）① 情報整理 | ログ・関連情報の要約 | 対象範囲の決定 | 要約に事実誤認がないか | 必要な情報が過不足なく揃っている | AIを使わない場合との作業時間と、修正箇所数を記録する |
| （記入欄） | | | | | |
| （記入欄） | | | | | |

5. AIの提案をそのまま採用せず、**最低1か所は自分で修正してください。** 工程の分け方が粗すぎる、確認項目が抜けている、完了条件があいまい、といった点が修正の対象になります。
6. 修正した箇所と、その理由を書きます（例：「③の工程は、要約と一次報告文の作成という2つの作業が混ざっていたため分割した」）。
7. 最後に、AIに任せた部分と、自分が判断した部分を、誰かに説明するつもりで一文にまとめます。
8. AI活用による変化を確認する方法を決めます。作業を実施した場合は、作業時間、修正箇所数、抜け漏れ、手戻りなどを記録してください。短縮時間だけでなく、確認や修正に要した時間も含めて振り返ります。

### 演習を通じて確認しておきたいこと

この演習は、提出や採点を前提にしたものではありません。ただし、次のような形で自分の手元に記録を残しておくと、後で振り返ったり、周囲に説明したりする際に役立ちます。

- タスク分解表（上記の6列を埋めたもの）
- AIへ実際に送った依頼文
- 自分が行った修正の内容と、その理由
- AI活用による変化を確認する方法、または実施後に記録した結果

### 補足演習：架空データを使う場合

担当業務がまだ無い、または実データを使いにくい場合は、次の架空の障害ログを使って一次報告文の作成を練習できます。個人情報・社外秘情報を含まない、練習用のダミーデータです。

```
2026-08-03 10:12:05 ERROR  OrderService: PaymentGateway への接続がタイムアウト（再試行 3/3 失敗）
2026-08-03 10:12:40 WARN   OrderService: 注文キューの滞留数が閾値を超過（512件）
2026-08-03 10:15:10 ERROR  OrderService: PaymentGateway への接続がタイムアウト（再試行 3/3 失敗）
2026-08-03 10:20:00 INFO   OrderService: 手動フェイルオーバー実施、処理再開
```

このログをAIに渡し、①発生時刻、②事象、③影響範囲、④現時点で確認できていない事項、を含む一次報告文のドラフトを作らせてみましょう。ドラフトができたら、ログの内容と照合し、AIが憶測で書いてしまった部分（例：原因の断定）がないかを確認し、必要な修正を加えてください。

## まとめ

- **AI Delegation**：本教材では、最終的な責任と判断を人が保持したまま、任せる範囲・渡す情報・確認方法・完了条件を人が決めたうえで、仕事の一部をAIに任せることを指す
- **Task Decomposition**：仕事を任せられる単位に分解すること。分解しないと何を任せてよいか判断できない
- **Human in the Loop**：依頼前に任せる範囲・渡す情報・完了条件を決め、業務への影響に応じた方法で結果を確認すること。長時間・複数工程の作業では、実行中にもチェックポイントを置く
- **Workflow**：AI活用を単発のやり取りではなく、依頼から確認・修正・完了・効果の記録までの一連の流れとして設計する視点

一言でいうと、Lv.2のAI Delegationとは、**自分の仕事を適切に分け、AIへ任せ、人が結果を確認し、業務上の成果まで責任を持って完了させること**です。それができたとき、あなたは「自分の仕事で成果に変えられる人」に近づいています。
